# PART 3 — UNIVERSAL ARTICLE IMAGE URL SUPPORT

## Current problem

The website currently depends on a limited number of external image hosts.

The Next.js configuration previously contained specific hosts such as:

- images.unsplash.com
- images.openai.com
- thumbs.dreamstime.com

An iStock image URL was saved successfully in `articles.cover_image_url`, but the frontend displayed:

`/images/article-image-unavailable.svg`

I do not want editors to keep modifying `next.config.mjs` every time they choose a different image provider.

## Main requirement

**The editorial system should accept publicly accessible image URLs from any legitimate image-hosting website, rather than restricting editors to a predefined list of domains.**

Examples include:
- Google-hosted images.
- Google Drive image links.
- Google Photos links, where accessible.
- iStock.
- Shutterstock.
- Getty Images.
- Unsplash.
- Pexels.
- Pixabay.
- Dreamstime.
- Wikimedia Commons.
- Supabase Storage.
- Other publicly accessible image-hosting services.

Do not hardcode a short list of image domains as the only accepted sources.

## Technical implementation

Audit the current image rendering architecture.

Determine whether the issue comes from:
- `next/image` remote domain restrictions.
- Next.js image optimization.
- External hotlink protection.
- Expired URLs.
- Non-direct image URLs.
- Google Drive sharing URLs.
- Authentication-protected images.
- Incorrect URL transformations.
- Frontend image error handling.

Implement an appropriate architecture.

### A. Support arbitrary direct image URLs

Where appropriate, use standard browser image rendering for externally hosted images rather than requiring Next.js remote host registration.

An external image should not fail merely because its hostname is absent from `remotePatterns`.

### B. Handle Google Drive and other sharing links

Editors may paste links copied from Google Drive or other cloud services.

Implement a URL resolver for supported sharing-link formats.

Where a provider offers a reliable direct image URL, resolve it before rendering.

Do not assume that every Google search result, webpage, or sharing link is an image file.

If a link requires authentication, has expired, or cannot provide publicly accessible image content, display a useful validation message.

### C. Image proxy or ingestion system

Evaluate whether a secure server-side image proxy or Supabase Storage ingestion system is the best approach for reliable rendering.

If implementing an image proxy:
- Only allow HTTP/HTTPS URLs.
- Block localhost, private IP ranges, link-local addresses and internal services.
- Validate every redirect destination.
- Prevent SSRF vulnerabilities.
- Enforce reasonable file-size limits.
- Validate actual image content types.
- Reject HTML, scripts and non-image responses.
- Set appropriate timeouts.
- Prevent unbounded downloads.
- Do not expose private server credentials.

If an image is publicly accessible and can be safely retrieved, support rendering it without manual domain configuration.

### D. Supabase Storage

Use the existing Supabase Storage infrastructure as the preferred permanent storage solution.

Provide a way to upload article cover images directly from the editorial dashboard.

When an editor uploads an image:
1. Upload it to the appropriate Supabase Storage bucket.
2. Obtain its public URL.
3. Save the URL in `articles.cover_image_url`.
4. Display it in the article preview.
5. Preserve the image when publishing.

Keep external URL support as well. Do not force every editor to upload an image when a valid public image URL is available.

### E. Image failure handling

Implement:
- A proper fallback image.
- Clear validation messages in the editorial dashboard.
- Image preview before submission.
- Image availability checks before publication.
- Graceful handling of failed image loading.
- Appropriate aspect ratios and object-fit behaviour.
- No broken image icons or blank image containers.

Do not claim that every URL on the internet can be guaranteed to work. The requirement is to support any publicly accessible, valid image URL that the browser or secure image-fetching service can retrieve.

### F. Existing article images

Do not destroy or overwrite existing image URLs.

Test the existing article:

`the-disappearing-first-job`

Article ID:

`34975faf-ee73-4083-a731-42fff22aac57`

Its existing image URL is:

`https://media.istockphoto.com/id/1302759602/photo/senior-asian-manager-receiving-the-resume-document-from-young-asian-woman-graduate-before.jpg?s=612x612&w=0&k=20&c=Uv1nGjjaZ1njbY1jWjMOFVtulVPfMqrQLsF6VEBKC0E=`

Identify why it fails and make the rendering system handle this failure correctly.

Do not assume adding the iStock hostname alone solves the problem.
